MODULE 04

CLAUDE.md & Project Memory

Give Claude persistent, deep knowledge of your project. Learn the memory hierarchy, write effective CLAUDE.md files, and manage context across sessions.

📖 ~20 min 🧠 Context engineering

What is CLAUDE.md?

CLAUDE.md is a plain Markdown file that Claude Code reads automatically at the start of every session. Think of it as your project's onboarding document for Claude — it contains everything Claude needs to know to work effectively: coding conventions, architecture decisions, tech stack, testing requirements, and any rules you want followed consistently.

Without CLAUDE.md, Claude starts every session with zero project context. With a good CLAUDE.md, Claude immediately understands your codebase the way a veteran team member does.

ℹ️
Quick Generate with /init

Run /init inside a Claude Code session and it will scan your project and generate an initial CLAUDE.md for you. Use this as a starting point, then refine it.

The Memory Hierarchy

Claude Code supports multiple CLAUDE.md files that stack on top of each other. Files closer to the project override global ones.

File locations — loading order (lowest to highest priority)
1. Global (your machine, all projects)
~/.claude/CLAUDE.md

2. Project root (shared with team via git)
/your-project/CLAUDE.md

3. Project local (personal, gitignored)
/your-project/CLAUDE.local.md

4. Subdirectory (applies only when working in that dir)
/your-project/src/components/CLAUDE.md
FileScopeGitUse For
~/.claude/CLAUDE.mdAll projectsNoYour personal style preferences, universal tools
CLAUDE.md (root)This project✅ CommitTeam conventions, architecture, shared rules
CLAUDE.local.mdThis project❌ GitignorePersonal notes, local paths, private context
src/CLAUDE.mdThat subdirectory✅ CommitSubsystem-specific rules (e.g., "all components must use Storybook")

Writing an Effective CLAUDE.md

The best CLAUDE.md files are specific, actionable, and focus on what Claude would otherwise get wrong. Here's a complete real-world example:

markdown — CLAUDE.md (complete example)
# Project: Horizon — E-commerce Platform

## Tech Stack
- Frontend: Next.js 14 (App Router), TypeScript, Tailwind CSS
- Backend: Node.js with Express, PostgreSQL with Prisma ORM
- Testing: Vitest + Testing Library, Playwright for e2e
- CI/CD: GitHub Actions

## Architecture
- `/src/app/` — Next.js App Router pages and layouts
- `/src/components/` — Reusable UI components (always use TypeScript)
- `/src/lib/` — Shared utilities, API client, db helpers
- `/src/server/` — Express API routes and middleware
- `/prisma/` — Database schema and migrations
- `/tests/` — All test files mirror the src/ structure

## Coding Standards
- TypeScript strict mode is enabled — no `any` types
- All components must be functional (no class components)
- Prefer named exports over default exports
- Use Zod for all runtime validation (already installed)
- Error boundaries required for all page-level components
- All async operations must have explicit error handling

## Naming Conventions
- Components: PascalCase (e.g., UserProfile.tsx)
- Utilities: camelCase (e.g., formatCurrency.ts)
- Test files: co-located with source (e.g., Button.test.tsx)
- API routes: kebab-case (e.g., /api/user-profile)
- DB table names: snake_case (following Prisma convention)

## Testing Requirements
- Unit tests required for all utility functions
- Component tests required for interactive components
- Run `npm test` before suggesting a task is complete
- Minimum 80% coverage — run `npm run test:coverage` to check

## Common Commands
```bash
npm run dev          # Start development server
npm test             # Run unit tests
npm run test:e2e     # Run Playwright e2e tests
npm run db:migrate   # Run Prisma migrations
npm run lint         # ESLint check
npm run typecheck    # TypeScript type check
```

## Important Context
- The `useAuth` hook is our custom auth wrapper — never use
  next-auth directly in components
- All prices are stored in cents (integer) in the DB
- Feature flags are in `src/lib/flags.ts` — check before
  adding conditional logic
- DO NOT modify the Prisma schema without running a migration

What to Include

⚙️
Tech Stack & Versions
Framework versions, key packages, any legacy constraints Claude needs to respect.
📁
Directory Structure
Where things live so Claude places new files in the right location automatically.
📏
Coding Standards
Naming conventions, TypeScript settings, forbidden patterns, style rules.
🧪
Testing Requirements
What tests are required, which test runner to use, coverage expectations.
⌨️
Common Commands
Dev server, test runner, build, lint, deploy — so Claude uses the right commands.
⚠️
Gotchas & Rules
"Never do X", "Always use Y instead of Z", project-specific pitfalls.

What NOT to Include

  • Very long explanations — keep it concise and scannable
  • Things that are obvious from the code itself
  • Sensitive credentials or secrets (use environment variables)
  • Extensive API documentation — link to docs instead and use WebFetch
  • Outdated information — stale CLAUDE.md can be worse than none

Global CLAUDE.md (Personal Preferences)

Your ~/.claude/CLAUDE.md applies to all projects and is great for personal preferences that you want everywhere.

markdown — ~/.claude/CLAUDE.md
# Personal Global Preferences

## My Preferences
- I prefer functional programming patterns over OOP where practical
- Always explain non-obvious code changes with inline comments
- When you complete a task, summarize what you changed and why
- If a task seems ambiguous, ask ONE clarifying question before proceeding

## My Setup
- I use nvm for Node.js version management
- Preferred test runner is Vitest (not Jest) for new projects
- I use conventional commits: feat/fix/chore/docs/refactor/test

## Things I Dislike
- Excessive abstraction ("YAGNI" — you ain't gonna need it)
- Magic numbers without constants
- Mutation of function arguments

Session Memory & the /compact Command

Within a session, Claude maintains a conversation context window. As sessions grow long, context fills up — here's how to manage it.

Terminal — managing context
# Check current context usage
You: /status
  Model: claude-sonnet-4-6
  Context: 78,432 / 200,000 tokens (39%)
  Session ID: abc123

# When context is high (~80%), compact it
You: /compact retain the auth refactor decisions and JWT schema

  Compacting conversation...
  Context reduced to 12,400 tokens. Retained: auth architecture decisions,
  JWT token structure, test patterns used.

# Or compact with specific retention hint
You: /compact keep the list of files changed and why
💡
CLAUDE.md vs Session Memory

CLAUDE.md is for permanent project knowledge (it's always loaded). Session memory is for the current task's context. After a session, important decisions should be added to CLAUDE.md if they're worth remembering long-term.

Maintenance Best Practices

  • Treat CLAUDE.md like real documentation — keep it up to date as the project evolves
  • Add a rule whenever Claude makes a mistake it shouldn't repeat: "Never use class components" if you had to correct that twice
  • Commit CLAUDE.md to git — it's a team resource, not just yours
  • Separate personal preferences into CLAUDE.local.md and add that to .gitignore
  • Use subsystem CLAUDE.md files for large monorepos — a frontend CLAUDE.md in src/frontend/, a separate one in src/api/
  • Periodically run /init again and see what it suggests — it might catch outdated entries
