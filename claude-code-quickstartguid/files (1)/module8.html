MODULE 08

Skills

The most powerful extensibility mechanism in Claude Code — self-contained capability packages that auto-activate based on context, bundle executable scripts, and work across every Claude product.

📖 ~30 min 🎯 High-impact feature

What are Skills?

Skills are folders containing a SKILL.md file (plus optional scripts and resources) that give Claude a specialized playbook for a class of tasks. Unlike slash commands which you invoke manually, skills can activate automatically when Claude recognizes the current task matches the skill's description.

Think of skills as onboarding guides you write for Claude: "When you're doing X, here's the expert playbook to follow — and here are scripts you can run."

ℹ️
Skills Merged with Commands

In recent versions, slash commands and skills were unified. A file at .claude/commands/deploy.md and a skill at .claude/skills/deploy/SKILL.md both create /deploy and behave identically. Skills add the extras: bundled scripts, supporting files, and automatic invocation.

Skills vs Commands vs MCP vs Agents

Understanding where each mechanism fits helps you pick the right tool:

📝 Slash Commands

Single Markdown file. Simple prompt templates. Invoked by typing /name.

→ User invokes manually

🎯 Skills

Folder with SKILL.md + optional scripts/files. Rich playbooks with executable helpers.

→ Auto or manual invocation

🔌 MCP Servers

External service connections (GitHub, Jira, etc.). Provide new tools with live data access.

→ Always available when connected

🤖 Agents

Parallel Claude instances for concurrent work. Spawned explicitly to delegate tasks.

→ Parallel execution
💡
Decision Rule

If the same instructions are repeated across sessions → make it a skill. If it needs live external data → use MCP. If it needs to run in parallel → use an agent. If it's a one-off task → just prompt.

Anatomy of a Skill

Every skill is a directory with a SKILL.md file at its root. The file has two parts: YAML frontmatter and Markdown instructions.

markdown — SKILL.md anatomy
--- ← frontmatter start
name: code-review
  # becomes the /slash-command name

description: Thorough code review covering security, performance,
             and maintainability. Use when reviewing PRs, diffs,
             or any files for quality. Activates automatically
             when user asks to "review" code.
  # Claude uses this to decide auto-activation.
  # Be specific — this is your relevance signal.

allowed-tools: Read, Grep, Glob, Bash(git diff:*)
  # Whitelist tools this skill can use

argument-hint: [file, directory, or PR diff]
model: claude-opus-4-6
  # Optional: override model for this skill
--- ← frontmatter end

# Review Instructions — Markdown content begins here

When reviewing code, always check:
1. **Security**: injection risks, auth holes, exposed secrets
2. **Performance**: N+1 queries, unnecessary re-renders
3. **Maintainability**: naming, DRY violations, complexity
4. **Tests**: are new code paths covered?

Provide file:line references for each finding.
Group findings by severity: CRITICAL, HIGH, MEDIUM, LOW.

Auto-Invocation vs Manual Invocation

Skills have two invocation modes, controlled by the frontmatter and how Claude interprets your task.

Automatic Invocation

When Claude processes your message, it scans all skill frontmatter (~100 tokens per skill) and loads any that match. This happens transparently — you don't need to type a command.

How auto-invocation works
You have a skill with this description:
description: Systematic debugging workflow. Use when encountering
             bugs, test failures, or unexpected behavior, before
             proposing any fixes.

You say:
You: The login tests are failing after my last commit, help me debug

Claude: [automatically loads debug skill and follows its playbook]
  ● Reading test output...
  ● Checking git diff since last pass...
  ● Identifying root cause...

Manual Invocation

You can always invoke a skill explicitly with its slash command, regardless of context:

session
/code-review               ← invoke the code-review skill directly
/deploy staging            ← invoke with argument
/help                      ← see all available skills in autocomplete

Bundling Scripts — The Real Power

Skills can include executable scripts in any language. Claude reads the SKILL.md instructions, then uses Bash to run the bundled scripts as part of completing the task. This is the "progressive disclosure" architecture: scripts only load their output into context, not their source code.

Example: Codebase Visualizer Skill

markdown — .claude/skills/codebase-viz/SKILL.md
---
name: codebase-viz
description: Generate an interactive collapsible HTML tree visualization
             of the codebase. Use when asked to visualize project structure,
             generate a directory map, or explain codebase organization.
allowed-tools: Bash, Read
---

Generate an interactive codebase visualization:

1. Run the bundled script to scan the project:
   `python3 {SKILL_PATH}/scripts/scan.py --output /tmp/tree.json`

2. Run the visualization generator:
   `python3 {SKILL_PATH}/scripts/render.py /tmp/tree.json > /tmp/viz.html`

3. Open the result:
   `open /tmp/viz.html`

The output is an interactive HTML page with collapsible directories,
color-coded file types, and file size indicators.
ℹ️
{SKILL_PATH} Variable

Use {SKILL_PATH} in your SKILL.md to reference the skill's directory. This ensures scripts are found regardless of where the skill is installed.

Example: Database Query Skill with Schema Context

markdown — .claude/skills/db-query/SKILL.md
---
name: db-query
description: Write and execute safe PostgreSQL queries. Use when the user
             asks to query data, analyze records, or investigate database
             state. Never modifies data without explicit confirmation.
allowed-tools: Read, Bash(psql *), Bash(cat *)
---

Database query assistance for this project.

First, read the schema for context:
`cat {SKILL_PATH}/schema.sql`

Rules for safe querying:
1. Always use LIMIT on exploratory queries
2. Never run DELETE/UPDATE/DROP without explicit user confirmation
3. For large datasets, use EXPLAIN ANALYZE first
4. Prefer CTEs over nested subqueries for readability

Connection: `psql $DATABASE_URL`

The schema.sql file in the skill folder is loaded only when the skill activates — not on every session startup — keeping context lean.

Production-Ready Skill Examples

1. Test-Driven Development Skill

markdown — .claude/skills/tdd/SKILL.md
---
name: tdd
description: Test-driven development workflow. Automatically use when
             implementing any new feature or bugfix. Forces tests-first
             approach before any implementation code.
allowed-tools: Read, Write, Edit, Bash(npm *), Bash(npx *)
---

# TDD Workflow

**CRITICAL**: Never write implementation code before tests.

## Red Phase
1. Understand the requirement fully — ask if unclear
2. Write a failing test that captures the requirement
3. Run the test — confirm it FAILS with the right error
4. `npm test -- --testPathPattern=[test-file]`

## Green Phase
1. Write the MINIMUM code to make the test pass
2. No extra features, no premature optimization
3. Run the test — confirm it PASSES
4. Run the full test suite — confirm nothing is broken

## Refactor Phase
1. Improve the code structure without changing behavior
2. Remove duplication, improve naming, simplify logic
3. Run tests after every change — all must stay green

If at any point the user pushes to skip tests, remind them
of the TDD contract and ask why they want to skip.

2. Git Worktree Workflow Skill

markdown — .claude/skills/worktree/SKILL.md
---
name: worktree
description: Create and manage isolated git worktrees for parallel feature
             development. Use when asked to work on multiple features
             simultaneously or start a new isolated task.
allowed-tools: Bash(git *)
argument-hint: <feature-name>
---

# Git Worktree Management

## Creating a new worktree
1. Ensure we're on main: `git checkout main && git pull`
2. Generate a branch name: `feat/{ARGUMENTS}` (kebab-case, max 40 chars)
3. Create worktree: `git worktree add ../wt-{ARGUMENTS} -b feat/{ARGUMENTS}`
4. Confirm: `git worktree list`
5. Print: "Worktree created at ../wt-{ARGUMENTS}"
   "Run: cd ../wt-{ARGUMENTS} && claude"

## Listing worktrees
`git worktree list`

## Merging & cleaning up
1. Merge/PR the feature branch
2. Remove worktree: `git worktree remove ../wt-{ARGUMENTS}`
3. Delete branch: `git branch -d feat/{ARGUMENTS}`

3. API Conventions Reference Skill

markdown — .claude/skills/api-conventions/SKILL.md
---
name: api-conventions
description: API design standards for this codebase. Auto-load when
             writing any API routes, controllers, or HTTP handlers.
             Reference content — enhances all API work automatically.
---

# API Conventions for this Project

## Response Format (always use)
```json
{
  "data": { ... },
  "meta": { "timestamp": "ISO8601", "version": "1.0" },
  "error": null
}
```

## Error Responses
```json
{
  "data": null,
  "error": { "code": "VALIDATION_ERROR", "message": "...", "field": "email" }
}
```

## Route Naming
- Collections: `GET /users` — not `/getUsers`
- Items: `GET /users/:id`
- Actions: `POST /users/:id/deactivate`
- Nested: `GET /users/:id/orders` (max 2 levels deep)

## Status Codes
- 200: Success with data
- 201: Created (include Location header)
- 204: Success, no body (DELETE)
- 400: Validation error
- 401: Not authenticated
- 403: Not authorized
- 404: Not found
- 422: Business logic error
- 500: Server error (never expose internals)

Skills vs Commands — When to Use Each

Use Skills When...Use Commands When...
You want auto-activation — Claude should just know to use it You always want to explicitly invoke it
The skill needs bundled scripts or reference files A single Markdown prompt file is sufficient
You're encoding expert domain knowledge (security, testing, API design) You need a simple workflow shortcut (commit, PR description)
The skill should work across projects (personal skills folder) The command is project-specific
You want team-wide ambient guidance (API conventions loaded automatically) You want a quick callable action
💡
In Practice: Use Both

The best setups combine both: skills for ambient expertise that auto-loads (TDD approach, API conventions, security awareness) and commands for explicit workflow shortcuts (commit, deploy, review). They're complementary, not competing.

Performance & Token Usage

Skills are designed to be efficient. Claude Code uses a progressive disclosure model:

  • At session start, only skill frontmatter is scanned (~100 tokens per skill) to determine relevance
  • When a skill activates, only its SKILL.md content loads into context (~1–5k tokens typically)
  • Bundled resource files (schema.sql, checklist.md) only load if the skill's instructions reference them
  • Script source code never enters the context — only the script's output does
  • Result: you can have dozens of skills installed with minimal overhead

Token Budget Estimate

10 skills installed × ~100 tokens each = ~1,000 tokens for discovery. When 1-2 skills activate per task, add ~3–8k tokens. Total overhead for a well-stocked skills setup: typically under 2% of the context window.
