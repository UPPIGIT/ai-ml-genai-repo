Hooks — Automating the Lifecycle

Hooks are scripts, HTTP endpoints, or LLM prompts that fire automatically at specific points in Claude Code's lifecycle. They let you add deterministic, automated behavior without relying on Claude to remember.

Hook EventWhen it FiresCommon Uses
PreToolUseBefore Claude uses any toolLog actions, block dangerous commands, ask for permission
PostToolUseAfter a tool completes successfullyFormat code, run linter, send notifications
PostToolUseFailureAfter a tool failsError alerting, diagnostics
StopWhen Claude finishes respondingDesktop notification, save summary, run tests
SubagentStopWhen a subagent finishesAggregate results, cleanup

Configuring Hooks

Hooks are defined in .claude/settings.json. Each hook specifies which event triggers it, which tools to match (for tool hooks), and what command/endpoint/prompt to call.

json — .claude/settings.json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "npx prettier --write \"${TOOL_INPUT_PATH}\""
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "notify-send 'Claude Code' 'Task finished'"
          }
        ]
      }
    ],
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "~/.claude/hooks/log-bash.sh"
          }
        ]
      }
    ]
  }
}

Practical Hook Examples

1. Auto-Format on Every Write

json — PostToolUse hook
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Write|Edit",
      "hooks": [{
        "type": "command",
        "command": "prettier --write \"${TOOL_INPUT_PATH}\" 2>/dev/null; eslint --fix \"${TOOL_INPUT_PATH}\" 2>/dev/null; true"
      }]
    }]
  }
}

2. Block Dangerous Bash Commands

bash — ~/.claude/hooks/guard.sh
#!/bin/bash
# Block destructive commands from being run without explicit confirmation

INPUT=$(cat)  # Hook receives JSON on stdin
COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command // ""')

# Block patterns
if echo "$COMMAND" | grep -qE '(rm -rf|DROP TABLE|DELETE FROM [a-z]+$|truncate)'; then
  echo '{"decision": "block", "message": "Blocked potentially destructive command. Please confirm explicitly."}'
  exit 0
fi

# Allow all other commands
echo '{"decision": "allow"}'
json — Register the hook
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{
        "type": "command",
        "command": "~/.claude/hooks/guard.sh"
      }]
    }]
  }
}

3. Desktop Notification on Completion

bash — Multi-platform notification
#!/bin/bash
# ~/.claude/hooks/notify.sh
# Platform-aware desktop notification

MESSAGE="${1:-Claude finished}"

case "$(uname -s)" in
  Darwin)
    osascript -e "display notification \"$MESSAGE\" with title \"Claude Code\""
    ;;
  Linux)
    notify-send "Claude Code" "$MESSAGE" 2>/dev/null || true
    ;;
  CYGWIN*|MINGW*)
    powershell -Command "New-BurntToastNotification -Text 'Claude Code','$MESSAGE'"
    ;;
esac

4. Auto-Run Tests After File Changes

json — Run tests after write
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Write|Edit",
      "hooks": [{
        "type": "command",
        "command": "npm test --passWithNoTests --bail 2>&1 | tail -5",
        "async": true
      }]
    }]
  }
}
💡
async: true for Non-Blocking Hooks

Set "async": true on hooks that are slow (like test runs) so they don't block Claude Code while they execute. The hook runs in the background.

Subagents — Parallel Work

Subagents are separate Claude Code instances spawned to work in parallel. The orchestrating Claude delegates tasks to subagents and combines their results. This is how Claude Code handles complex multi-track tasks efficiently.

Terminal — Spawning subagents
You: Run a comprehensive audit of our codebase:
     - Security vulnerabilities
     - Performance bottlenecks  
     - Accessibility issues in the UI
     - Dependency updates needed
     Do all four in parallel.

Claude: I'll spawn 4 specialized subagents for parallel analysis...

  [Subagent 1] Security audit → scanning src/ for vulnerabilities
  [Subagent 2] Performance analysis → reading src/, checking bundles
  [Subagent 3] Accessibility audit → scanning components for a11y
  [Subagent 4] Dependency check → running npm audit + npm outdated

  [All complete in 45s — vs ~160s sequentially]

  Aggregate Report:
  Security: 2 HIGH issues found in auth/...
  Performance: 3 bundle-size wins identified...
  Accessibility: 7 missing aria-labels...
  Dependencies: 4 updates recommended...

Custom Subagent Definitions

You can define specialized subagents with their own instructions and tool access in .claude/agents/.

markdown — .claude/agents/security-auditor.md
---
name: security-auditor
description: Use when performing security analysis, vulnerability scanning,
             or code reviews focused on security. Triggers automatically
             for security-related tasks.
allowed-tools: Read, Grep, Glob
model: claude-opus-4-6
---

You are a security expert specializing in web application security.

When analyzing code:
1. Look for OWASP Top 10 vulnerabilities
2. Check for hardcoded secrets using regex patterns
3. Verify authentication and authorization on all routes
4. Look for SQL/NoSQL injection vectors
5. Check for XSS vulnerabilities in output rendering

Report findings by severity: CRITICAL, HIGH, MEDIUM, LOW
Include: file path, line number, vulnerability type, remediation.
ℹ️
Skills vs Agents

Skills (.claude/skills/) are loaded automatically when their description matches the current task. Agents (.claude/agents/) are explicitly spawned by the orchestrating Claude when it decides to delegate work. Skills influence behavior; agents do parallel work.

Git Worktrees for Isolated Sessions

The --worktree flag creates an isolated git worktree so Claude Code's changes don't interfere with your current branch. Perfect for experimenting or running multiple tasks in parallel.

bash — Worktree sessions
# Start an isolated session for a risky refactor
claude --worktree refactor-auth
Created worktree: /tmp/claude-worktree-refactor-auth
Working in isolation from your main branch.

# Run two feature implementations in parallel
# Terminal 1:
claude --worktree feature-dark-mode
# Terminal 2 (simultaneously):
claude --worktree feature-notifications

# Worktree is auto-cleaned if no changes are made
# Otherwise, it remains for you to review and merge

CI/CD Integration

Claude Code's headless mode makes it a powerful addition to GitHub Actions, GitLab CI, and other pipelines.

GitHub Actions: Auto-Review PRs

yaml — .github/workflows/claude-review.yml
name: Claude Code Review

on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Install Claude Code
        run: curl -fsSL https://claude.ai/install.sh | bash

      - name: Run security review
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          claude -p "Review this PR diff for security vulnerabilities.
            Output findings as GitHub-flavored Markdown." \
            --allowedTools Read,Grep,Glob,Bash(git diff:*) \
            --output-format text \
            --max-turns 10 > review.md

      - name: Post review comment
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const review = fs.readFileSync('review.md', 'utf8');
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: `## 🤖 Claude Code Security Review\n\n${review}`
            });

Auto-Generate Changelogs

bash — In a release script
#!/bin/bash
# Generate changelog from git history since last tag

LAST_TAG=$(git describe --tags --abbrev=0 2>/dev/null || echo "HEAD~50")
GIT_LOG=$(git log $LAST_TAG..HEAD --oneline)

claude -p "Generate a user-facing CHANGELOG.md entry from these commits:

$GIT_LOG

Group by: Features, Bug Fixes, Performance, Dependencies.
Write in plain English that non-developers can understand.
Output only the Markdown, nothing else." \
  --output-format text \
  --model claude-haiku-4-5-20251001 > CHANGELOG_NEW.md

cat CHANGELOG_NEW.md CHANGELOG.md > CHANGELOG_MERGED.md
mv CHANGELOG_MERGED.md CHANGELOG.md

Power User Tips & Patterns

⚡
The "Rubber Duck" Pattern

Start with --no-tools for design discussions. "Walk me through how you'd design a caching layer for this API." Get the architecture right before any code is written.

⚡
Session per Feature Branch

Use claude --worktree feature-name for each feature. This maps your Claude Code sessions directly to git branches, making it easy to context-switch between features without confusion.

⚡
The "Read → Plan → Code → Test" Loop

For any non-trivial task: 1) Ask Claude to read the relevant files first, 2) Ask for a plan, 3) Approve or adjust the plan, 4) Execute, 5) Run tests. This loop produces higher quality results than one-shot prompts.

⚡
Use /compact Proactively

Don't wait for context to fill up. After completing a major task within a session, run /compact keep the architecture decisions and changed files list. Smaller context = faster responses and lower cost.

⚡
Batch Automation with Shell Scripts

Combine Claude Code with shell scripting for powerful batch operations: iterate over a list of files, call claude -p for each, collect outputs. Example: generate API documentation for every route file in one script.
