The Perfect Python CLAUDE.md

This file is Claude's brain about your project. It's loaded every session. Be specific, be concise, be ruthless about accuracy.
CLAUDE.md is the difference between Claude guessing your conventions and knowing them. Invest 20 minutes here, save hours everywhere else.
CLAUDE.md — Complete Python Template (copy & customise)
# Project: My FastAPI Application REST API for user management. Python 3.12 + FastAPI + SQLAlchemy 2.0 + Postgres. ## Environment - Python 3.12 (use `python3`, never `python`) - Virtual env at `.venv/` — always activated before any work - Dependencies: fastapi, uvicorn, sqlalchemy, pydantic, alembic, python-dotenv ## Commands ```bash uvicorn app.main:app --reload # dev server pytest # run all tests pytest -x -v # stop on first fail, verbose ruff check . --fix # lint + auto-fix ruff format . # format (like black) mypy app/ --strict # type check alembic revision --autogenerate # new migration alembic upgrade head # apply migrations ``` ## Architecture app/main.py → FastAPI app, lifespan, middleware app/models/ → SQLAlchemy ORM models (one file per domain) app/schemas/ → Pydantic request/response schemas app/routers/ → Route handlers (one file per resource) app/services/ → Business logic (NO db calls in routers!) app/deps.py → FastAPI dependency functions app/database.py → SQLAlchemy engine + session factory tests/conftest.py → Shared fixtures (test db, test client) ## Our Conventions - **Type hints everywhere** — all functions must be fully annotated - **Pydantic v2** for ALL request/response validation — never raw dicts in routes - **Never import Session directly** — use `Annotated[Session, Depends(get_db)]` - **Async routes** — all route handlers must be `async def` - **Service layer** — business logic goes in `app/services/`, not in routers - **Error handling** — raise `HTTPException` from services, not from models - **Naming**: snake_case files, PascalCase classes, UPPER_CASE constants ## Testing Rules - Every new function needs a test in `tests/` - Use `pytest.mark.parametrize` for multiple input cases - Use factory fixtures in `conftest.py` — never hardcode test data inline - Mock external API calls — never hit real endpoints in tests - Minimum 80% coverage enforced by CI ## Gotchas - Local dev requires `.env` with `DATABASE_URL` set (see `.env.example`) - Run `alembic upgrade head` after pulling any branch with new migrations - The `payments/` module uses Stripe — don't refactor without checking stripe.py first - SQLAlchemy 2.0 style only — no legacy `session.query()` syntax ## Git Workflow - Branch naming: `feat/description`, `fix/description`, `chore/description` - Conventional commits: `feat(auth): add JWT refresh` - PRs require: passing CI + 1 review + no mypy errors

--- name: pytest testing patterns description: Testing patterns for this Python project using pytest. Auto-activate when writing, reviewing, or fixing tests. Use when asked to add tests or improve test coverage. allowed tools: Read, Bash(pytest), Grep, Glob --- # Testing Patterns ## Structure: AAA Pattern All tests MUST follow Arrange → Act → Assert: ```python def test_create_user(db_session, user_factory): # Arrange payload = UserCreate(email="test@example.com", name="Alice") # Act user = create_user(db_session, payload) # Assert assert user.id is not None assert user.email == "test@example.com" ``` ## Fixtures (always in conftest.py) ```python @pytest.fixture def db_session(): engine = create_engine("sqlite:///:memory:") Base.metadata.create_all(engine) with Session(engine) as session: yield session ``` ## Parametrize for edge cases ```python @pytest.mark.parametrize("email,valid", [ ("good@email.com", True), ("bad-email", False), ("", False), (None, False), ]) def test_email_validation(email, valid): assert is_valid_email(email) == valid ``` ## Mocking External Services Always mock: HTTP calls, email sending, payment processing, S3. ```python def test_send_email(mocker): mock_send = mocker.patch("app.email.resend.emails.send") send_welcome_email(user) mock_send.assert_called_once() ```
.claude/skills/pydantic-schemas/SKILL.md
--- name: pydantic v2 schemas description: Pydantic v2 schema patterns. Use when creating or reviewing API schemas, request/response models, or validation logic. allowed tools: Read, Grep --- # Pydantic v2 Schema Patterns ## Schema Hierarchy ```python from pydantic import BaseModel, EmailStr, Field, model_validator # Base — shared fields class UserBase(BaseModel): email: EmailStr name: str = Field(min_length=1, max_length=100) # Create — request body (no id) class UserCreate(UserBase): password: str = Field(min_length=8) # Read — response (includes id, timestamps) class UserRead(UserBase): id: int created_at: datetime model_config = ConfigDict(from_attributes=True) # Update — all optional for PATCH class UserUpdate(BaseModel): name: str | None = None email: EmailStr | None = None ``` ## Custom Validators ```python @model_validator(mode="after") def passwords_match(self) -> "UserCreate": if self.password != self.confirm_password: raise ValueError("Passwords do not match") return self ```

.claude/settings.json — Python hooks
{ "permissions": { "allow": ["Read:*", "Write:app/**", "Write:tests/**", "Bash:pytest*", "Bash:ruff*", "Bash:mypy*", "Bash:pip install*", "Bash:git*"], "deny": ["Read:.env*", "Bash:sudo*", "Bash:rm -rf*"] }, "hooks": { // ── After writing any Python file: lint + type-check "PostToolUse": [ { "matcher": "Write:*.py", "hooks": [{ "type": "command", "command": "ruff check --fix \"$CLAUDE_TOOL_INPUT_FILE\" && mypy \"$CLAUDE_TOOL_INPUT_FILE\"", "timeout": 15 }] }, // ── After writing test files: auto-run the tests { "matcher": "Write:tests/*.py", "hooks": [{ "type": "command", "command": "pytest tests/ -x -q 2>&1 | tail -20", "timeout": 60 }] } ], // ── Before any bash command: block dangerous patterns "PreToolUse": [ { "matcher": "Bash", "hooks": [{ "type": "command", "command": "scripts/check_safe.sh" }] } ] } }
scripts/check_safe.sh — PreToolUse safety script
#!/bin/bash # Exit 2 to BLOCK the command. Exit 0 to ALLOW it. COMMAND="$CLAUDE_TOOL_INPUT_COMMAND" # Block destructive patterns if echo "$COMMAND" | grep -qE '(rm -rf|DROP TABLE|DELETE FROM [^W]|sudo)'; then echo "❌ BLOCKED: Dangerous command pattern detected" >&2 exit 2 # exit 2 = Claude stops and shows error fi # Block accessing secrets if echo "$COMMAND" | grep -qE 'cat .env|echo .env|less .env'; then echo "❌ BLOCKED: .env access not permitted" >&2 exit 2 fi exit 0 # allow everything else
✓ Result
With these hooks, every time Claude writes a Python file, ruff auto-fixes style issues and mypy catches type errors instantly. When it writes tests, they run immediately. Claude sees the output and self-corrects — no manual steps.

• POST /auth/login (verifies password, returns token)

Bug Fix ❌ Vague
My tests are failing, fix them.
Bug Fix ✓ Specific
Run pytest tests/test_users.py -v and fix all failures. The tests were passing before I refactored the UserService. Don't change the test assertions — only fix the implementation in @app/services/user_service.py.
Refactor ❌ Vague
Refactor my code.
Refactor ✓ Specific
Refactor @app/routes/users.py. Move all DB logic into a new app/services/user_service.py. Route handlers should only handle HTTP concerns (request parsing, response formatting). Keep the same endpoint signatures. All existing tests must still pass after refactor.

## FastAPI Patterns ```python # ── Dependency injection (always use Annotated) from typing import Annotated DbSession = Annotated[Session, Depends(get_db)] CurrentUser = Annotated[User, Depends(get_current_user)] @router.get("/me", response_model=UserRead) async def get_me(db: DbSession, user: CurrentUser): return user # ── Lifespan (replace @app.on_event) @asynccontextmanager async def lifespan(app: FastAPI): await startup() yield await shutdown() # ── Test client @pytest.fixture def client(db_session): app.dependency_overrides[get_db] = lambda: db_session with TestClient(app) as c: yield c ```
CLAUDE.md addition — Django specific
## Django Conventions Commands: python manage.py runserver # dev python manage.py test # tests python manage.py makemigrations # new migration python manage.py migrate # apply Patterns: - Use `select_related()` / `prefetch_related()` to avoid N+1 queries - Fat models, thin views — business logic in model methods - Custom managers for reusable query sets - All views use class-based views (CBV) with mixins - `settings/base.py` + `settings/dev.py` + `settings/prod.py` - Use `django-environ` for environment variables - Tests use `pytest-django` with `@pytest.mark.django_db`
CLAUDE.md addition — Data Science / ML
## Data Science Conventions Stack: Python 3.12 · pandas 2.x · numpy · scikit-learn · matplotlib Paths: data/raw/ → original, never modified data/processed/ → cleaned, feature-engineered models/ → serialized model files (.pkl, .joblib) notebooks/ → exploration only, not production src/ → production Python modules Rules: - Use `pathlib.Path`, never string paths - DataFrames: always set explicit dtypes on load - Use `pd.read_csv(..., dtype={...})` not implicit inference - Models saved with `joblib.dump()`, versioned by date - Seed all random operations: `np.random.seed(42)`, `random_state=42` - Log training metrics with MLflow or simple CSV log Commands: jupyter notebook # explore python src/train.py # train model pytest tests/ -m "not slow" # fast tests only

Advanced Usage

Complex Multi-file Tasks

Big refactors, new features that span many files, database migrations — how to tackle them safely with Claude.
For large tasks: always use Plan Mode first. Read the plan. Then switch to Auto Accept. Commit after each working milestone — not at the end.
1
Switch to Plan Mode (Shift + Tab twice)
Describe the full feature. Claude outlines all files it will touch, the order, and any risks. Read it carefully before approving.
2
Approve plan or correct it before any code is written
If the plan touches the wrong files, says so in plain English. "Don't modify the payments module — only the user module." Claude will re-plan.
3
Switch to Auto Accept (Shift + Tab) and confirm
Claude executes without interrupting you on each step. Hooks will run ruff + mypy + pytest automatically after each file write.
4
Commit after each working phase
git add . && git commit -m "feat(users): add service layer" — small commits mean easy rollback if something goes wrong later.
5
Esc Esc to rewind if anything goes sideways
Claude's rewind rolls back to any previous checkpoint without losing your git history. Then try a different approach.
Multi-file task prompt examples
# ── Complete new feature across multiple files # (Use Plan Mode first!) Implement a Role-Based Access Control (RBAC) system: 1. New SQLAlchemy model: `Role` (id, name, permissions JSON) 2. Add `role_id FK` to the User model 3. Alembic migration for both changes 4. New `require_role(role_name)` dependency in deps.py 5. Apply `require_role("admin")` to all admin routes in @app/routers/admin.py 6. Tests for all new behaviour Commit each step separately. Run tests after each commit. # ── Large-scale type annotation Add strict type hints to ALL files in @app/services/. Process them one file at a time. After each file, run: `mypy app/services/<filename>.py --strict` Fix all errors before moving to the next file. Do NOT use `Any` as a shortcut. # ── Database schema change + migration Add a `profile_picture_url` field (nullable str, max 500 chars) to User. Steps: 1. Update SQLAlchemy model in @app/models/user.py 2. Update Pydantic schemas (UserRead, UserUpdate) in @app/schemas/user.py 3. Run `alembic revision --autogenerate -m "add profile picture url"` 4. Review the generated migration, then `alembic upgrade head` 5. Update affected tests
