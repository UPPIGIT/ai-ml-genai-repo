01.01

What this course teaches

This course teaches Claude Code Skills from the ground up — not just what they are, but how they work internally, why they're designed that way, and how to use that understanding to build Skills that actually work in production.

By the end you'll be able to explain Skills to anyone, build them confidently, debug them when they misbehave, and make smart decisions about when to use Skills vs other Claude Code features.

What you already have

You have Claude Code installed, a todo app on GitHub, custom /audit and /write_test commands, and GitHub Actions set up. We'll use all of this. Your existing commands become Skills in Module 3.

01.02

How to read this course

Each module follows the same structure: concept first, then the hands-on implication, then a summary you can reference later. There are quiz questions at the end of each module — answer them honestly before checking.

Everything is grounded in your todo app. When a concept is abstract, we apply it immediately to something concrete.

01.03

Why Skills — the 30-second case

Custom commands are instructions you type. Skills are instructions Claude finds on its own — and they come with a full supporting folder of scripts, references, and templates.

The result: you stop managing your workflow and Claude starts managing it for you. You say "write tests for this" and the right playbook loads automatically, with the right tools, the right constraints, and the right output format — every time.

The core promise

Skills make your expertise reusable and auto-applying. You write the playbook once. Claude follows it whenever it's relevant — without you remembering to invoke it.

Module 02

What are Skills?

The mental model, internal architecture, and triggering mechanism — explained from first principles.

02.01

The mental model — onboarding guide for AI

The best way to understand Skills is to think about what happens when a new developer joins your team. You don't dump the entire codebase on them on day one. You give them an onboarding guide: what the project is, how to run it, what the conventions are, what to do when X happens.

A Skill is exactly that — but written for Claude. It packages your expertise into a structured playbook that Claude can pick up, understand, and apply when the situation calls for it.

The critical difference from a custom command is that a custom command is something you consciously invoke. A Skill is something Claude discovers and uses. You stop being the task router and become the knowledge author.

Teaching framing

When explaining Skills to others, use this analogy: "A Skill is to Claude what a well-written SOP is to a new hire. The SOP doesn't need to be handed to them for every task — they know when to reach for it."

02.02

The three-level loading architecture

This is the most important thing to understand about how Skills work under the hood. Skills don't load all at once — they load progressively, in three levels.

LevelWhat loadsWhenToken cost
1 — Metadataname + description from frontmatterSession start, always~100 per skill
2 — InstructionsFull SKILL.md bodyWhen skill triggers~5,000
3 — ResourcesFiles in references/ and assets/Only when needed0 until read

Level 1 is tiny — scanning 20 skills at session start costs about 2,000 tokens total. Level 2 only loads when you actually need the skill. Level 3 files only load if Claude decides to read them while working.

This is why Skills can include dozens of reference files without bloating the context window. A references/ folder with 10 files costs zero tokens unless Claude needs one of them.

Why this matters

It means you can be generous with supporting material. Add examples, templates, reference docs, helper scripts — all at near-zero cost. The right files load only when the task requires them.

02.03

What Claude actually sees — the system prompt injection

At session start, Claude Code scans all skill folders and builds an <available_skills> XML block that gets injected into Claude's system prompt. It looks like this:

<!-- Injected into system prompt at session start -->
<available_skills>
  <skill>
    <n>audit</n>
    <description>
      Audits Python code for bugs, security issues...
      Use when asked to review, audit, or check quality.
    </description>
    <location>.claude/skills/audit/</location>
  </skill>
  <skill>
    <n>write-test</n>
    <description>
      Writes pytest tests for Python todo app...
      Use when asked to write tests or improve coverage.
    </description>
    <location>.claude/skills/write-test/</location>
  </skill>
</available_skills>

When Claude receives a message from you, it checks this block and decides whether any skill is relevant. If yes, it uses bash to read the full SKILL.md file — which is Level 2 loading.

02.04

Auto-trigger vs manual invocation — the full picture

Every skill supports two ways to trigger it. Understanding both is essential for designing skills that behave predictably.

Manual — you type /name

  • Always fires, no matching needed
  • Good for side-effect actions
  • User is in explicit control
  • Same as custom commands
  • Works even with poor description

Auto — Claude decides

  • Fires based on description match
  • Good for expertise skills
  • Transparent to the user
  • Requires good description
  • Can be disabled per-skill

The two modes aren't mutually exclusive. Most skills support both. You might auto-trigger write-test when you say "test the add function" and also manually invoke it with /write-test todo.py when you want to be explicit.

02.05

Skills vs instructions — the key difference

This distinction matters more than anything else when teaching others:

Rules in CLAUDE.md tell Claude what to do. Claude will usually follow them. Skills also tell Claude what to do — but they load only when relevant, they come with supporting resources, and they can be auto-discovered.

Neither Skills nor CLAUDE.md guarantee execution the way Hooks do. If you need something to always happen, use Hooks. If you need Claude to follow a playbook when a certain kind of task comes up, use Skills.

Common misconception

Skills don't run code. They're instructions injected into Claude's context. The bash scripts in your scripts/ folder only run if Claude decides to execute them — Skills don't automatically fire scripts.

Module 02 — Check your understanding

Q1. A skill's SKILL.md is 8,000 tokens long. How many tokens does it cost at session start?

8,000 tokens — the full file is always read
~100 tokens — only metadata (name + description) loads
0 tokens — skills don't affect the context window
Only the frontmatter metadata loads at session start. The full SKILL.md body (Level 2) only loads when the skill is actually triggered.

Q2. You want a /deploy skill that Claude should never trigger automatically. Which frontmatter field controls this?

user-invocable: false
disable-model-invocation: true
auto-trigger: false
disable-model-invocation: true prevents Claude from auto-triggering the skill. user-invocable: false does the opposite — it prevents manual /command invocation but still allows auto-trigger.

Q3. Where does the available_skills block get injected?

Into every user message
Into the system prompt at session start
Into the first assistant response
Claude Code injects available_skills into the system prompt when the session starts. This is why skills are available throughout a session without being re-scanned.

Module 03

Creating Your First Skill

Convert your existing commands into Skills and write descriptions that reliably trigger.

03.01

The folder structure

Every skill is a folder inside .claude/skills/. The folder name becomes the command name. Inside it, only SKILL.md is required.

.claude/ ├── commands/ │ ├── audit.md ← old commands still work │ └── write_test.md └── skills/ ├── audit/ │ ├── SKILL.md ← required │ ├── scripts/ │ ├── references/ │ └── assets/ └── write-test/ ├── SKILL.md └── references/ └── pytest_patterns.md

The three optional subdirectories serve distinct purposes: scripts/ holds executable files Claude can run via bash. references/ holds documentation loaded into context on demand. assets/ holds templates and binary files.

03.02

The SKILL.md structure — frontmatter + body

Every SKILL.md has two parts separated by ---. The frontmatter configures how the skill behaves. The body tells Claude what to do.

audit/SKILL.md---
name: audit
description: Audits Python code for bugs, security issues,
             input validation, and test coverage. Use when
             asked to review, audit, or check code quality —
             even if the user just says "look at this".
version: 1.0.0
---

# Code Audit

Audit $ARGUMENTS. If no argument, audit the whole project.

## Steps
1. Read all relevant .py files first
2. Check security: hardcoded secrets, injection risks...
... rest of your existing audit.md content ...
Migrating your existing commands

Your existing audit.md content goes directly into the SKILL.md body. Add the frontmatter on top. That's the entire migration.

03.03

Writing descriptions that actually trigger — the formula

The description field is the most important thing you write. It's the only signal Claude uses to decide whether to auto-trigger your skill. A bad description means your skill sits unused no matter how good the instructions are.

The formula that works consistently:

# FORMULA
[What it does] + [domain nouns].
Use when asked to [verb list] — even if [edge cases].

# BAD — too vague, will undertrigger
description: Audits code.

# GOOD — specific domain, clear trigger verbs, edge case
description: Audits Python code for bugs, security issues,
             input validation, error handling, and test
             coverage gaps. Use when asked to review,
             audit, check, or inspect code quality — even
             if the user just says "look at this file" or
             "something seems wrong here".

Three rules for descriptions:

  • Write in third person — it gets injected into the system prompt
  • Include the verb list explicitly with "Use when asked to..."
  • Add at least one "even if..." clause for edge case coverage
The undertriggering problem

Claude naturally errs on the side of not using a skill if it's unsure. Make your description a little "pushy" — explicitly tell Claude when to use it. Vague descriptions cause the skill to be ignored most of the time.

03.04

Testing with the 20-query eval method

After writing a description, test it with 20 realistic queries — half that should trigger your skill, half that shouldn't. Save them as a JSON file in your skill folder:

audit/eval.json[
  { "query": "can you review todo.py",           "should": true  },
  { "query": "something seems off with validation", "should": true  },
  { "query": "check for bugs in my code",           "should": true  },
  { "query": "write tests for add_todo",            "should": false },
  { "query": "what does complete_todo do?",         "should": false },
  { "query": "audit my flask routes",              "should": true  }
]

Use realistic queries — include typos, casual speech, file paths, and abbreviations. Simple queries like "review file X" are poor tests. The edge cases are what matter.

03.05

Step-by-step: migrate audit.md to a Skill

# Step 1 — Create the folder
mkdir -p .claude/skills/audit

# Step 2 — Copy your existing command
cp .claude/commands/audit.md .claude/skills/audit/SKILL.md

# Step 3 — Open SKILL.md and add frontmatter at the top
.claude/skills/audit/SKILL.md — add this at line 1---
name: audit
description: Audits Python code for bugs, security issues,
             input validation, error handling, and test
             coverage gaps. Use when asked to review, audit,
             check, or inspect code quality — even if the
             user just says "look at this" or "something
             seems wrong".
version: 1.0.0
---

# Code Audit   ← your existing content starts here
# Step 4 — Test it. Open Claude Code and say:
"can you review todo.py for any issues"

# Should auto-trigger without you typing /audit
# Also verify manual trigger still works:
/audit src/

Repeat the same steps for write_test.md → write-test/SKILL.md.

Module 03 — Key takeaways

  • Folder name = command name. .claude/skills/audit/ creates /audit.
  • Only SKILL.md is required. Supporting folders are optional.
  • Migration is one-step. Copy the .md file, add frontmatter on top.
  • Description quality determines auto-trigger accuracy. Use the verb list formula.
  • Test with 20 queries — mix of should-trigger and should-not-trigger.

Module 04

Configuration & Multi-file Skills

Every frontmatter field, invocation control, and how to use supporting files effectively.

04.01

Every frontmatter field explained

FieldRequiredWhat it does
nameYesMax 64 chars, lowercase + hyphens only. Becomes the /command name.
descriptionYesMax 1024 chars. The auto-trigger signal. Write in third person.
versionNoSemantic version for tracking. Good practice for shared skills.
allowed-toolsNoRestrict which tools Claude can use. e.g. "Read, Write"
disable-model-invocationNoSet true to block auto-trigger. Manual /command only.
user-invocableNoSet false to hide /command. Auto-trigger only.
04.02

disable-model-invocation — for dangerous side effects

Some skills should only run when you explicitly decide to run them. Deployment, git commits, sending messages, deleting data — these have real-world side effects. You don't want Claude auto-deciding to deploy your app because the code looks ready.

.claude/skills/deploy/SKILL.md---
name: deploy
description: Runs pre-deploy checks for the todo app and
             verifies readiness. Use when explicitly asked
             to deploy or ship.
disable-model-invocation: true   ← only /deploy works
---

With this set, Claude will never auto-trigger /deploy no matter what you say. Only typing /deploy explicitly will fire it.

04.03

user-invocable: false — background knowledge

Some skills aren't actions — they're knowledge. A skill that explains your legacy data format, your team's architecture decisions, or historical context shouldn't expose a /command. There's nothing meaningful to do when you type /legacy-context. But Claude should load it automatically when the task touches that area.

.claude/skills/legacy-storage/SKILL.md---
name: legacy-storage
description: Context about the old JSON storage format used
             before the SQLite migration. Load when the user
             asks about todos.json, old data, or migration.
user-invocable: false   ← no /command exposed
---

The original todos.json format stored todos as a flat
array with integer IDs starting at 1...
04.04

allowed-tools — least privilege for safety

By default a skill can use any tool. allowed-tools restricts this. A read-only audit skill has no business running bash commands. A test-writer shouldn't be touching the network.

---
name: audit
allowed-tools: "Read, Grep, Glob"  ← read-only
---

---
name: write-test
allowed-tools: "Read, Write, Bash" ← can write + run pytest
---

---
name: deploy
allowed-tools: "Bash, Read"        ← can run shell commands
---
04.05

Adding supporting files — the real power

Multi-file skills are where things get genuinely powerful. You can bundle reference docs, templates, and scripts alongside your instructions — and they only load when needed.

Here's a fully built write-test skill with all three supporting folders:

.claude/skills/write-test/ ├── SKILL.md ← instructions + frontmatter ├── references/ │ └── pytest_patterns.md ← team conventions ├── assets/ │ └── test_template.py ← base test file template └── scripts/ └── run_coverage.sh ← run tests + show coverage
references/pytest_patterns.md# Pytest conventions for this project

- Always use tmp_path fixture for file operations
- Group tests in classes: TestCreate, TestRead, TestUpdate, TestDelete
- Naming: test_<action>_<condition>_<expected>
- Never import from conftest — use fixtures directly
scripts/run_coverage.sh#!/bin/bash
pytest --cov=todo --cov-report=term-missing -q
echo "Coverage complete."
SKILL.md body — referencing the supporting files# Write Tests

Before writing, read references/pytest_patterns.md for
team conventions. Use assets/test_template.py as the
base for all new test files.

After writing tests, run scripts/run_coverage.sh and
report the coverage percentage.
Progressive disclosure in practice

Claude only reads pytest_patterns.md if it decides the conventions are needed. If you ask for one quick test, it might not bother. If you ask for comprehensive coverage, it will. Zero token cost either way until the file is actually read.

Module 05

Skills vs Other Features

How Skills fit alongside CLAUDE.md, Hooks, Custom Commands, and MCP Servers.

05.01

The complete decision framework

Each Claude Code feature occupies a distinct role. The mistake most people make is trying to use one feature for everything. Here's when to reach for each:

FeatureUse when you need...Guarantees?
CLAUDE.mdAlways-on project context, style rules, architecture notesNo
SkillsOn-demand expertise with auto-discovery and supporting filesNo
Custom CommandsSimple manual invocations (legacy, no auto-trigger needed)No
HooksGuaranteed execution — enforcement, not guidanceYes
MCP ServersExternal tools — GitHub, databases, Playwright, APIsYes
05.02

Skills vs CLAUDE.md — where to put what

The most common question. Use this decision tree:

Should this information be in CLAUDE.md or a Skill?
YES → Is it always relevant regardless of task?
→ CLAUDE.md. Stack, project structure, coding style, naming conventions, architecture. Claude reads this always.
NO → Is it only relevant for certain task types?
→ Skill. Testing conventions → write-test skill. Audit criteria → audit skill. Deploy checklist → deploy skill.
ALSO → Does it come with scripts, templates, or reference docs?
→ Always a Skill. CLAUDE.md is text-only. Skills have a full folder.

Practical rule: CLAUDE.md holds your project's identity. Skills hold your project's playbooks.

05.03

Skills vs Hooks — guidance vs enforcement

This is the most important distinction to teach others because it's the one that causes the most confusion.

The rule

Use Skills when you want Claude to do something well. Use Hooks when you need something to always happen, no exceptions.

Concrete example with your todo app:

  • write-test Skill — guides Claude to write good tests when testing is needed
  • PostToolUse Hook — runs pytest after every file edit, guaranteed, even if Claude forgets

The Skill makes the tests good. The Hook makes the tests run. You need both.

05.04

Everything working together — the full stack

Here's what a production setup looks like with all features working in concert:

# CLAUDE.md — always-on context
Stack: Python 3.11, Flask, SQLite
Rules: raise ValueError for empty titles, use pytest
Commands: pytest, python app.py

# Skills — on-demand playbooks
audit/        → triggered by "review my code"
write-test/   → triggered by "write tests for X"
deploy/       → triggered only by /deploy (disabled auto)

# Hooks — guaranteed execution (.claude/settings.json)
PostToolUse   → run pytest after every file edit
PreToolUse    → block rm -rf and .env modifications
Stop          → desktop notification when done

# MCP Servers — external tools
GitHub MCP    → @claude creates PRs from issues
Playwright    → browser testing for the Flask UI

Each feature does what it's best at. Nothing overlaps. The whole is greater than the sum of its parts.

Module 05 — Check your understanding

Q1. You want Claude to always run linting after editing Python files. Which feature?

A Skill with instructions to lint
A PostToolUse Hook
A rule in CLAUDE.md
Hooks guarantee execution. Skills and CLAUDE.md are guidance — Claude might follow them most of the time but not always. For enforcement, always use Hooks.

Q2. Your coding style rules (4-space indent, snake_case, etc.) should go in:

CLAUDE.md — always relevant

Style rules apply to every coding task, so they belong in CLAUDE.md which is always loaded. A Skill only loads when triggered — you'd miss the style rules on tasks that don't match the trigger.

Module 07

Troubleshooting Skills

Every failure mode, how to diagnose it, and how to fix it.

07.01

Skill not appearing at all

Run /help inside Claude Code. If your skill doesn't appear, work through this checklist:

  • Is the file named exactly SKILL.md (not skill.md or Skill.md)?
  • Is it inside a folder inside .claude/skills/ — not directly in .claude/skills/?
  • Does the frontmatter have both name and description fields?
  • Is the name value valid — lowercase, hyphens only, under 64 chars?
  • Are the --- delimiters present on their own lines with no trailing spaces?
07.02

Skill exists but never auto-triggers

The skill appears in /help but Claude never loads it automatically. This is an undertriggering problem — the description isn't matching your natural language well enough.

  • Add the "Use when asked to..." clause if missing
  • Add "even if..." edge case clauses
  • Include more synonyms in the verb list
  • Check you're writing in third person
  • Use the 20-query eval method to find the gaps
# Before — undertriggering
description: Audits Python code.

# After — reliable triggering
description: Audits Python code for bugs, security issues,
             and test coverage. Use when asked to review,
             audit, check, inspect, or analyse code — even
             if the user just says "something looks off"
             or "can you look at this file".
07.03

Skill triggers on everything (overtriggering)

Claude loads the skill even when it's not needed. Narrow the description:

  • Remove broad verbs like "use when working with code"
  • Add exclusion clauses: "Do not use when the user is asking questions, only when asking for changes"
  • Split into two more focused skills if the description is trying to cover too much
07.04

Skill loads but Claude ignores the instructions

  • Are the instructions too vague? Be specific — "check for empty titles" not "validate inputs"
  • Is there a conflict with CLAUDE.md? The skill body should not contradict project rules
  • Is allowed-tools blocking a tool the instructions need? e.g. instructions say "run pytest" but allowed-tools: "Read"
  • Is the SKILL.md over 500 lines? Split it — large files cause important instructions to be deprioritised
07.05
