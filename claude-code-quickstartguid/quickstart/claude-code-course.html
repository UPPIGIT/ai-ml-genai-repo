MODULE 01

Getting Started

Install Claude Code and initialize your first project in under 2 minutes.

Claude Code is an AI-powered agentic coding tool that lives in your terminal. It reads your entire codebase, understands context, and helps you build — all through natural language conversation.

1

Install Claude Code

Requires Node.js 18+. Run this single command in your terminal to install globally:

BASH
# Install Claude Code globally via curl curl -fsSL https://claude.ai/install.sh | bash # Verify the installation succeeded claude --version
2

Navigate to Your Project

Move into an existing project directory, or create a brand new one:

BASH
# Enter an existing project cd ~/projects/my-app # OR create a new project from scratch mkdir my-new-app && cd my-new-app git init
3

Launch Claude & Initialize

Run claude to launch, then type /init to scan the codebase. Claude explores your files and auto-generates a starter CLAUDE.md memory file.

CLAUDE CODE TERMINAL
claude Welcome to Claude Code. Type /help for commands. # Inside Claude Code, run: /init ✓ Scanning your codebase... ✓ Detected: Next.js · TypeScript · Prisma · Tailwind ✓ Generated CLAUDE.md — your project memory file → Review and refine this file to improve Claude's context
💡
Pro Tip: Always run /init first, then manually refine the generated CLAUDE.md. Add domain knowledge, team conventions, and gotchas that Claude couldn't infer from the code alone.
MODULE 02

Understanding CLAUDE.md

Claude's persistent memory — automatically loaded at the start of every session.

CLAUDE.md is a plain Markdown file that acts as Claude's brain for your project. It defines what Claude knows, how the project is structured, and what conventions to follow — every single session.

🧱

WHAT to Include

  • Tech stack & versions
  • Architecture overview
  • Directory map
  • Module descriptions
🎯

WHY to Write It

  • Purpose of each module
  • Design decisions made
  • Gotchas Claude can't infer
  • Team conventions
⚙️

HOW it Helps

  • Build / test commands
  • Lint & format pipelines
  • Deployment steps
  • Workflow automation
CLAUDE.md — Full Example
# Project: MyApp FastAPI REST API + React SPA + PostgreSQL ## Tech Stack - Backend: Python 3.12 · FastAPI · SQLAlchemy · Alembic - Frontend: React 18 · TypeScript · Vite · Tailwind CSS - Database: PostgreSQL 16 via Docker Compose - Auth: JWT with refresh rotation (30min/7day) ## Commands npm run dev # Start frontend dev server (port 3000) npm run test # Run Jest test suite with coverage npm run lint # ESLint + Prettier check uvicorn main:app # Start FastAPI backend (port 8000) alembic upgrade head # Run pending DB migrations ## Architecture /app → Next.js App Router pages and layouts /lib → Shared utilities, hooks, and helpers /prisma → DB schema definitions and migrations /api → FastAPI route handlers and schemas /tests → Jest (frontend) + Pytest (backend) suites ## Gotchas - Always run alembic upgrade head before starting the API - Use pnpm not npm — lockfile is pnpm-lock.yaml - Env vars need to be in both .env AND .env.local for Next.js - The /api/legacy routes use REST v1 schema (don't migrate)
⚠️
Keep it under 200 lines. A bloated CLAUDE.md dilutes Claude's attention. Every line must add signal. Reference external docs with @filename syntax instead of copying content inline.
MODULE 03

Memory File Hierarchy

How Claude stacks memory files from global to subfolder scope.

Claude loads CLAUDE.md files in a layered order — more specific files append context to broader ones. This lets you share team-wide rules at the project level while scoping subfolder concerns precisely.

G

~/.claude/CLAUDE.md  GLOBAL

Applies to ALL your projects. Store personal preferences here: preferred coding style, your name, default tools, and general instructions that follow you everywhere.

P

~/.CLAUDE.md  MONOREPO ROOT

Sits at the repository root. Perfect for monorepos — defines shared conventions, shared tooling, and team standards across all packages. Committed to git.

R

/CLAUDE.md  PROJECT

The main project-level memory file. Architecture, commands, tech stack, conventions all go here. Committed to git and shared with the whole team on day one.

S

/frontend/CLAUDE.md  SUBFOLDER

Scoped to one subdirectory. Appends extra context — never overwrites the parent file. Use for complex modules with their own patterns or unique requirements.

📌
Three golden rules: Keep each file under 200 lines · Subfolder files append, never replace · Never overwrite parent context
MODULE 04

CLAUDE.md Best Practices

Habits that separate beginners from professional Claude Code users.

🔁

Init First, Refine Second

Let /init generate the skeleton, then edit by hand to add domain context, business logic constraints, and team decisions Claude couldn't infer.

📐

Be Specific in Instructions

Vague → vague results. Instead of "write clean code", write "use async/await everywhere, follow Airbnb style guide, prefer composition over inheritance."

🚫

Document Gotchas Explicitly

Write down what Claude cannot infer from source code: "Never use moment.js — we use date-fns" or "The /api/legacy endpoint uses v1 schema, never migrate it."

📎

Reference with @filename

Instead of pasting external docs into CLAUDE.md, use @filename to reference them. Claude reads them on demand without cluttering the memory file.

CLAUDE.md
API style: @docs/api-conventions.md DB schema: @prisma/schema.prisma Tests: @docs/testing-guide.md
✂️

Audit and Keep Concise

Every unnecessary line is noise that dilutes Claude's context. Every sprint, remove outdated info. Quality beats quantity — Claude's attention is finite.

🤝

Commit to Git for Teams

CLAUDE.md belongs in source control. Every team member gets identical Claude behavior. Add it to your onboarding checklist — it's as important as the README.

🧩
Add workflow rules too. Tell Claude things like "Always write a test before implementing a feature" or "Run npm run lint after every file change." These become automatic habits.
MODULE 05

Project File Structure

The canonical layout for a Claude Code–powered project.

Organizing your project correctly is what enables Claude's skills, hooks, and agents to auto-activate. The .claude/ directory is Claude's home base — every powerful feature lives there.

your-project/ ├── CLAUDE.md ← project memory (committed to git) ├── .claude/ ← Claude's home directory │ ├── settings.json ← permissions, hooks, model config │ ├── settings.local.json ← local overrides (gitignored!) │ └── skills/ ← auto-invoked knowledge packs │ ├── code-review/ │ │ └── SKILL.md ← review checklist & patterns │ ├── testing/ │ │ └── SKILL.md ← Jest + testing conventions │ └── helpers.py ← shared Python utilities ├── commands/ │ └── deploy.md ← custom /deploy slash command ├── agents/ │ └── security-reviewer.md ← subagent definition ├── src/ ← your application source code ├── arc/ ← architecture docs & diagrams └── .gitignore ← include: .claude/settings.local.json
🔑
Critical insight: The description field inside each SKILL.md is what Claude matches against your natural language requests. Getting it right is the difference between a skill that always fires vs. one that never activates.
MODULE 06

Adding Skills — The Superpower

Markdown knowledge packs that Claude auto-invokes via natural language matching.

Skills are Markdown files containing specialized knowledge, patterns, or step-by-step instructions. When your prompt semantically matches a skill's description, Claude automatically reads and applies it — no manual /skill command needed.

📁 Project Skill

Lives inside the project, committed to git. Every team member shares the same skills automatically.

.claude/skills/<name>/SKILL.md

Example: code-review/SKILL.md — fires when you ask Claude to "review this PR" or "check my code".

🏠 Personal Skill

Lives in your home directory. Private to you, applies across every project you work on.

~/.claude/skills/<name>/SKILL.md

Example: your personal my-style/SKILL.md with your preferred patterns and conventions.

.claude/skills/testing/SKILL.md — Complete Example
--- name: testing patterns description: Jest testing patterns for React components and API routes. Use when writing, reviewing, fixing, or generating tests. allowed tools: Read, Grep, Glob, Bash --- # Testing Patterns ## Core Philosophy - Use the AAA pattern: Arrange · Act · Assert (never mix them) - Prefer integration tests over unit tests for UI components - Use factory functions for test data — never hardcode IDs or dates - Mock at the boundary, not inside implementation details ## Component Test Template ```tsx import { render, screen } from '@testing-library/react'; import userEvent from '@testing-library/user-event'; import { createDefaultProps } from './factories'; describe('ComponentName', () => { it('renders correctly with default props', () => { // Arrange const props = createDefaultProps(); // Act render(<ComponentName {...props} />); // Assert expect(screen.getByRole('button', { name: /submit/i })).toBeInTheDocument(); }); it('calls onSubmit when form is submitted', async () => { const onSubmit = jest.fn(); render(<ComponentName onSubmit={onSubmit} />); await userEvent.click(screen.getByRole('button')); expect(onSubmit).toHaveBeenCalledOnce(); }); }); ``` ## Gotchas - Wrap async state updates in act() or use waitFor() - Use userEvent not fireEvent — it simulates real browser events - Never use getByTestId unless absolutely necessary — prefer roles
🎯
The description field is everything. Write it as: "Use when [trigger condition]" — be specific about when the skill applies. Claude reads all descriptions at session start and matches them semantically to your requests.

MODULE 08

Setting Up Hooks

Deterministic callbacks that fire before and after every Claude action.

Hooks are shell scripts called at specific lifecycle events. They're your safety net and automation layer — enforce policies, auto-run tests, block dangerous operations, or send notifications, all without AI decision-making.

PreToolUse PostToolUse Notification

⚡ PreToolUse

Runs before Claude executes any tool. Can block with exit code 2. Use to validate inputs or enforce security policies.

✅ PostToolUse

Runs after a tool completes. Auto-run lint, tests, or formatters every time Claude writes files to disk.

🔔 Notification

Fires on Claude events. Send Slack alerts, write audit logs, or notify your team when Claude makes significant changes.

.claude/settings.json — Hook Configuration
{ "hooks": { "PreToolUse": [ { "matcher": "Bash", ← fire before any Bash execution "hooks": [ { "type": "command", "command": "scripts/security-check.sh", "timeout": 5 } ] } ], "PostToolUse": [ { "matcher": "Write", ← fire after every file write "hooks": [ { "type": "command", "command": "npm run lint --fix && npm run test --passWithNoTests" } ] } ], "Notification": [ { "matcher": "*", ← fire on all events "hooks": [ { "type": "command", "command": "scripts/log-to-slack.sh" } ] } ] } }
🛑
Exit Codes: exit 0 = allow the action · exit 2 = BLOCK the action · other codes = allow but log the error. Security scripts must exit 2 on dangerous detections.
scripts/security-check.sh
#!/bin/bash # Reads the command Claude wants to run from stdin (JSON) INPUT=$(cat) COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command // ""') # Block destructive and dangerous operations DANGEROUS_PATTERNS='rm -rf /|DROP TABLE|sudo rm|dd if=|mkfs|format [A-Z]:' if echo "$COMMAND" | grep -qE "$DANGEROUS_PATTERNS"; then echo "🚫 Security hook: Blocked dangerous command" >&2 echo " Command: $COMMAND" >&2 exit 2 ← exit 2 = BLOCK fi # Log all Bash executions for audit trail echo "[$(date -u)] ALLOWED: $COMMAND" >> ~/.claude/audit.log exit 0 ← exit 0 = allow
MODULE 09

Permissions & Safety

Fine-grained allow/deny rules for every action Claude can take.

Claude's permissions system is a whitelist/blacklist in settings.json. Wildcards make rules expressive. The deny list always wins over the allow list — design accordingly.

.claude/settings.json — Permissions
{ "permissions": { "allow": [ "Read:*", ← read any file in the project "Bash:git:*", ← any git subcommand "Bash:npm:*", ← any npm command "Write:src/*", ← write to src directory only "Write:*.test.*", ← write test files anywhere "Write:*.md" ← write markdown docs ], "deny": [ "Read:env:*", ← NEVER read env variables "Read:.env*", ← NEVER read .env files "Bash:sudo:*", ← NEVER use sudo "Bash:curl:*", ← NEVER make external requests "Write:.env*" ← NEVER modify env files ] } }

✅ Recommended Allow Rules

  • Read:* — read all project files
  • Bash:git:* — all git operations
  • Bash:npm:* / Bash:pnpm:*
  • Write:src/* — source files only
  • Write:*.test.* — test files
  • Write:docs/* — documentation

🚫 Essential Deny Rules

  • Read:env:* — protect secrets
  • Read:.env* — protect env files
  • Bash:sudo:* — no elevation
  • Bash:curl:* — no egress
  • Write:.env* — protect config
  • Bash:rm -rf:* — no mass delete
🔐
Deny always beats Allow. If a tool matches both lists, it is blocked. Write allow rules broadly, deny rules narrowly. Use settings.local.json for personal overrides that shouldn't be committed to git.
MODULE 10

The 4-Layer Architecture

How Claude Code's components stack into a coherent, powerful system.

Understanding all four layers helps you decide where knowledge and rules belong. Each layer has a distinct role, activation mechanism, and level of authority.

L1

CLAUDE.md — Persistent Context & Rules

Always loaded at session start. Your project's DNA: tech stack, architecture, commands, conventions, and team rules. The foundation everything else builds on.

L2

Skills — Auto-Invoked Knowledge Packs

Domain-specific Markdown guides loaded on demand. Claude auto-discovers them by matching your natural language to each skill's description field. Focused and composable.

L3

Hooks — Safety Gates & Automation

Shell scripts at lifecycle events. PreToolUse enforces policies. PostToolUse automates follow-up. Fully deterministic — no AI involved, just code running reliably every time.

L4

Agents — Subagents with Independent Context

Separate Claude instances for specialized, parallel, or isolated tasks. Each agent has its own CLAUDE.md, permissions scope, and skills. Enables sophisticated multi-agent workflows.

🧠 When to Use Each Layer

  • CLAUDE.md — stable, always-relevant project facts
  • Skills — specialized domain knowledge
  • Hooks — non-negotiable enforcement rules
  • Agents — complex parallel work streams

⚠️ What Not to Mix

  • Don't put policy enforcement in CLAUDE.md (use Hooks)
  • Don't put stable facts in Skills (use CLAUDE.md)
  • Don't use Agents for simple single tasks
  • Don't put AI logic in Hooks (pure shell only)
MODULE 11

Daily Workflow Pattern

The repeatable loop that professional Claude Code users run every day.

This is the systematic workflow that makes you dramatically more productive. Each step has a clear purpose. Follow it consistently and you'll ship faster with fewer mistakes.

① cd project && claude
↓
② Shift + Tab + Tab → Enter Plan Mode
↓
③ Describe the feature intent clearly and completely
↓
④ Review Claude's plan — correct before it executes
↓
⑤ Shift + Tab → Auto Accept mode (let Claude run)
↓
/compact  — compress context window after milestones
↓
⑦ Esc Esc → Rewind if direction is wrong
↓
git commit -m "feat(scope): description"
↓
⑨ Start a fresh session for the next feature
🗺️

Plan Mode is Non-Negotiable

Forces Claude to think architecturally before touching files. You see the entire plan up front, can redirect course cheaply before any work is done.

⚡

Auto Accept for Speed

Once the plan is approved, Claude executes without per-step confirmation. High velocity — you review outcomes, not individual decisions. Trust the plan you signed off on.

🗜️

/compact for Long Sessions

Compresses conversation history to free up context window. Run after major milestones to keep Claude sharp and prevent degradation over long sessions.

🔒

Commit Early and Often

Small, focused commits are your undo button. If Claude goes sideways, git reset --hard HEAD~1 is your escape hatch. Never run Claude for hours uncommitted.
